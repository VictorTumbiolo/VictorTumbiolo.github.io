Work in progress. This project is still being built. What exists today is a baseline: a simplified ES-RNN for M4 Monthly with a plain LSTM in place of the paper's specialised network. Everything described under the roadmap after that, the other RNN variants, the gradient-boosted trees and the cross-dataset comparison, has not been built yet. Training the larger models has also outgrown a local machine, so the work is moving to AWS SageMaker AI.

What it is

ES-RNN (Smyl, 2020) is the method that won the M4 competition, a forecasting contest of 100,000 time series and 61 methods. It couples classical exponential smoothing, which handles each series' level and seasonality, with a recurrent neural network that learns the patterns shared across all series. The two are trained together, so the model is partly global and partly specific to each series.

This project re-implements it from the paper and the reference C++ code. The first step was a baseline covering only M4 Monthly (48,000 series, forecast horizon 18), with the paper's specialised network swapped for a plain one-layer LSTM. The goal of that baseline was to get the whole pipeline working end to end first: the smoothing layer, the network, the loss and the evaluation. Once that works, each variant from the paper can replace the LSTM in turn.

Roadmap and planned comparisons

The baseline is the common core. The plan is to build outward from it in three steps. Steps 2 and 3 are the comparisons: the ES-RNN variants against each other, and all of them against gradient-boosted decision trees.

  1. Baseline: plain-LSTM ES-RNN on M4 Monthly. Done The full pipeline trains and evaluates, and is scored against the official M4 results.
  2. Explore every RNN variant in the paper. Next Each M4 frequency in the paper is the common core plus a different network and a different smoothing setup. Each variant will be implemented and tested in turn, and compared with the others. Training these is where runs have started to take hours to days, which is why training is moving to SageMaker AI. A dilated, sequence-style model has been started in the repository's root.
  3. Compare against gradient-boosted decision trees. Planned The same forecasting task will be run with XGBoost and LightGBM as non-neural, global-model baselines, alongside the RNN variants.
  4. Compare all three families on other datasets. Planned ES-RNN variants, XGBoost and LightGBM will be compared on datasets beyond M4. This happens only once every RNN variant from the paper is fully implemented and tested.

Moving training to AWS SageMaker AI

The Monthly baseline trains in a reasonable time on a local machine. The other models are a different story. As the paper's larger variants come online, training is starting to take several hours to days per run, which is too slow to iterate on locally. So I have switched training over to AWS SageMaker AI.

  • Why

    Runs of several hours to days tie up a local machine and make it hard to try variants one after another. Moving them to SageMaker AI takes them off my own hardware.

  • Where I work

    I use SageMaker Studio as the working environment for the training side of the project.

  • Where the data lives

    I connect SageMaker Studio to S3 buckets and pull the data from them, instead of keeping the datasets on a local disk.

  • What it helps with

    It also fits the later steps: running XGBoost and LightGBM on the same data, and testing on datasets beyond M4.

How the training jobs run

Training runs as SageMaker training jobs, launched with an Estimator from the SageMaker Python SDK. For now the jobs run on an ml.m5.xlarge instance, which is a general-purpose CPU instance with no GPU.

That is a stopgap. I am waiting on a service-quota increase for a better GPU instance, since the default limit doesn't allow one. Until it is approved the jobs run on CPU, which is part of why they are slow, and moving to a GPU is the next step for training time.

How ES-RNN works

Each forecast goes through a differentiable exponential-smoothing step, a neural network and then back out of the smoothing step. Everything, including the per-series smoothing parameters, is trained jointly with one optimizer.

The smoothing layer

Holt–Winters-style smoothing without a trend (paper eq. 2), with a season length of 12 for Monthly data. 

l_t     = alpha * y_t / s_t + (1 - alpha) * l_{t-1}
s_{t+K} = beta  * y_t / l_t + (1 - beta)  * s_t
  • Per-series parameters. Each series has its own alpha, beta and 12 initial seasonality values, stored as learnable parameters. They are constrained as in the paper: alpha = sigmoid(alpha_raw), beta = sigmoid(beta_raw), and seasonality = exp(init_seasonality_raw). All raw values start at zero, so alpha and beta start at 0.5 and seasonality at 1.0.
  • The recursion runs over the whole series from its first point, and the initial level is seeded with the series' own first value (the paper doesn't say how to seed it).
  • Recomputed on every call from the current parameters, so there is no staleness between optimizer steps.

The loss

  • Pinball loss (paper eq. 7) with tau = 0.49 for Monthly. A value slightly below 0.5 counteracts the positive bias that comes from training in log space but evaluating in linear space.
  • Level wiggliness penalty. The squared second differences of log(l_{t+1} / l_t), averaged, which discourages the smoothed level from jumping around.
  • total = pinball + 50 * wiggliness, with the weight (LVP) 50 for Monthly.

The paper's variants, by frequency

Every frequency shares the same core: per-series level and seasonality, log-normalisation, a global network trained jointly with the smoothing parameters, a linear adapter to the horizon, pinball loss and the level penalty. What changes is the RNN connections and the smoothing setup. These are the variants to be implemented.

Season lengths for Monthly, Quarterly and Yearly follow the paper's convention of one season per year. Learning rates, epochs and learning-rate drops also differ per frequency: for example Monthly runs 10 epochs at 5e-4, Quarterly 15 epochs at 1e-3 dropping to 1e-4 at epoch 10, and Yearly 12 epochs at 1e-4. The paper also trains separate prediction-interval models, which this project doesn't cover.

The baseline corresponds to the Monthly row with the network replaced by a plain, non-dilated LSTM. The paper itself notes that standard non-dilated LSTM blocks "performed a bit worse" than dilated ones, which is the gap the dilated, residual and attentive variants are meant to close.

Reading the numbers

  • Gap to the winner: sMAPE +0.828, MASE +0.052, OWA +0.053.
  • Against the references: the baseline beats Theta, Comb and Naive2 on all three metrics. Its sMAPE edge over Theta is only 0.05, so that one is close to a tie, while the MASE and OWA margins are clearer.
  • A few hard series drive the average. Per-series sMAPE has a best of 0.10, a median of 7.26 and a worst of 155.31. The median sits well below the 12.95 mean, so a minority of hard series pull it up.
  • What closes the rest of the gap: the paper's residual dilated stack, full-series RNN state and ensembling. The baseline is a single plain-LSTM model with no ensemble.

Caveats. MASE is computed with a seasonal-naive scale (season 12) over each full training series, and hasn't been checked against the official M4 R code. The overall M4 figures in the competition paper (for example ES-RNN's 11.374 sMAPE) average all six frequencies, so they are not comparable with a Monthly-only run.

Baseline design

Notes on the baseline code, written from reading it.

Data

  • M4 Monthly: 48,000 series with an 18-point test set each. Training lengths run from 42 to 2,794 points, with a mean of about 216.3.
  • Domain one-hot. Each series' category (Demographic, Finance, Industry, Macro, Micro, Other) is one-hot encoded in a fixed sorted order and appended to the network input.
  • Loading checks that train and test ids match and that every test row has exactly 18 points, and builds the arrays with a single numpy conversion (a per-row pandas version was too slow for 48,000 rows).

Windowing

  • Series longer than 272 points are cut to their most recent 272 (paper section 3.3).
  • A window uses 12 points as input and the next 18 as the target, starting at every position, so series shorter than 30 points yield no windows.
  • That gives 7,519,476 windows across the 48,000 series, or 918 batches per epoch at a batch size of 8,192.
  • The dataset returns raw values only. Normalization happens inside the model, because the smoothing parameters have to take part in backpropagation.
  • The input window is 12 because the paper only says it should cover at least one seasonal period and was tuned by backtesting. 12 matches the reference C++ Monthly block.

The model

  • Network: a one-layer nn.LSTM with input size 7 (the normalized value plus the 6-way domain one-hot), hidden size 50, and a linear adapter from 50 to 18. It reads each 12-point window as a 12-step sequence of scalars.
  • Training forward pass: each window's full series is gathered, the smoothing recursion runs from the series' first point, the window and target are normalized, and the LSTM and adapter produce the 18 outputs in log space.
  • Inference: for every series, take the last 12 real points, run the recursion over the full series, normalize, predict, and denormalize. The seasonality for the 18 forecast steps is the last 12 seasonality values tiled.
  • Checkpoint: about 68 MB, almost all of it the stored series (about 52 MB of values and 13 MB of mask). Trainable parameters total about 684,700, of which about 672,000 are the per-series smoothing parameters. The LSTM and adapter together are only about 12,700.

How the baseline differs from the paper

It matches the paper's input window (12), output window (18), state size (50), learning rate (5e-4), tau (0.49), LVP (50) and maximum length (272), the log-normalized inputs, the domain one-hot, the joint training and the pinball loss in log space. It differs from the paper and its reference C++ in these ways.

  • Network. A plain one-layer LSTM, against the paper's residual dilated stack with dilations 1-3-6-12.
  • How the RNN is driven. The baseline treats each 12-point window as an independent 12-step sequence with the state reset every window. The paper and the C++ feed a whole window as one vector per timestep and step the RNN through the entire series with the state carried along.
  • Wiggliness scope. The window span here, against each series' whole level sequence in the C++.
  • Forecast seasonality. The last 12 values tiled here, against the updated seasonality extended past the end of the series in the C++.
  • Training granularity. Batches of 8,192 shuffled windows with one shared optimizer, against one Adam update per series in the C++, with a separate optimizer for the per-series parameters, gradient clipping at 20, input noise and a loss scaled by 2.
  • Initialisation. Per-series parameters start at zero here, while the C++ starts them differently.
  • Ensembling. The paper and the C++ use a simple ensemble (the data split in two, three runs each, forecasts averaged over the last five epochs). The baseline is a single model, a single run and a last-epoch forecast.
Known quirks and gotchas
  • Run the scripts from inside the baseline folder: the CSV paths are relative, and the data module loads the 215 MB training file at import time, so importing it from anywhere else fails.
  • The saved training script is set up as a quick test (EPOCHS = 1, *_TEST output names), while its messages and docstring still mention the full-run names and an out-of-date batch size.
  • Each window re-runs the smoothing recursion over the whole series, about 7.5 million recursions per epoch, which makes epochs slower than a per-series approach would be.
  • The validity mask is passed to the recursion but unused, so correctness relies on windows never reading padded positions.
  • Series order in a checkpoint is fixed by the order of the series list, and per-series parameters are indexed by position, not id.
  • The evaluation script imports the data module under a different name, so it only resolves with the repository root on the Python path.
