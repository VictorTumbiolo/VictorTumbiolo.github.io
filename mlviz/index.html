ML Algorithm Visualizer

An interactive app for training three classic machine-learning algorithms and looking inside them: an ID3 decision tree, a backpropagation neural network and a genetic algorithm. The algorithms come from Tom Mitchell's 1997 textbook Machine Learning, and every one is written from scratch with only the Java standard library. A Spring Boot API serves them to a React, TypeScript, Vite and React Flow frontend.

What it is

Most machine-learning demos hand you a trained model and a number. This one is built to show the learning: the tree being grown, the weights each neuron ended up with, a population of rule sets evolving generation by generation. Each algorithm has a results page, an About page that summarizes the matching chapter of the book, a dataset viewer, and at least one graph you can click into.

AlgorithmMitchellDatasetWhat you can see in the UI
ID3 decision treeCh. 3, Decision Tree LearningPlayTennisThe learned tree as an interactive graph, the training examples at every node, the IF–THEN rules and test accuracy.
Neural network (backpropagation)Ch. 4, Artificial Neural NetworksIrisThe network topology as a graph, each node's learned weights, accuracy, and a per-example prediction report.
Genetic algorithm (GABIL-style rule learner)Ch. 9, Genetic AlgorithmsPlayTennisA configurable archipelago of island populations, generation-by-generation evolution, each population's hypotheses, and bit-string rules decoded into readable IF–THEN form.

Written from scratch. The backend has no ML, math or data-science dependencies. pom.xml declares only spring-boot-starter-web (for HTTP and JSON) and spring-boot-starter-test. Entropy, information gain, forward propagation, backpropagation with momentum, selection, crossover, mutation and rule matching are all hand-written on top of java.util, java.lang.Math and a little java.lang.reflect.

Status: shelved. This is a longer project that I stopped working on. I got bored of it and moved on to the reinforcement-learning projects that make up the rest of this site. It works end to end, but it has some known bugs, listed in Known bugs and where it stands.

Architecture

A React single-page app talks JSON to a Spring Boot service, and the service is a thin shell around plain-Java algorithm classes.

Design principles

  • Thin web layer, plain-Java core

    Controllers parse a request DTO, call the algorithm and shape the response. The same classes still run from a main method: the original command-line harnesses are commented out in Driver and AlgoTester.

  • Train once, inspect many times

    The server keeps the latest trained model in memory, so after one training call the frontend can make any number of read-only calls to explore it without retraining.

  • DTOs at the boundary

    Request bodies bind to dedicated transfer objects, and the decision tree becomes a recursive JSON-friendly DTO. Parent pointers, String[] rows and StringBuilder rules never reach the client.

  • Visualization is the product

    Each algorithm gets a results page, an About page, a dataset viewer and at least one canvas you can click into for detail.

Cross-cutting choices

  • CORS. CorsConfig (a WebMvcConfigurer) allows http://localhost:5173, the Vite dev origin, for all routes and methods. Controllers also carry @CrossOrigin.
  • Console output as the HTTP response. NetworkController.trainNetwork and GAController.runGA temporarily swap System.out for a PrintStream over a ByteArrayOutputStream, run the algorithm, restore System.out and return the captured text. The algorithms keep printing as they did on the command line, and the browser shows that output in a results text area.
  • Two ways of loading files. ID3 loads datasets from the classpath (getClassLoader().getResourceAsStream), so its data is packaged in the jar. The NN and GA load data with Paths.get(fileName) relative to the working directory, which is why IrisTrain.txt, IrisTest.txt and Tennis-Train.txt also sit in Backend/.
  • Hand-written parsing. Every dataset is read with java.util.Scanner and String.split(" "). There is no CSV library.

The frontend: Vite, TypeScript, React, React Flow

Why this stack

  • Vite starts the dev server almost instantly and has fast hot module replacement, which suits a UI that is redesigned often while the algorithms are being tuned.
  • Strict TypeScript gives typed models for backend payloads. For example, ID3/Types.ts defines a recursive TreeNode type that mirrors TreeNodeFullDTO.
  • React Flow draws all three visualizations. It handles panning, zooming, a minimap, edge rendering and custom node components, so the code only has to compute nodes, edges and positions.

State management

  • IslandsContext wraps the whole app, above BrowserRouter. It holds the island configurations and the user-drawn migration edges, so an archipelago built on /ga_results is still there on /genetic_islands and /island/:id.
  • NeuralNetworkContext is mounted through a pathless layout route (<Route element={<NeuralNetworkProvider><Outlet/></NeuralNetworkProvider>}>). Its state is shared only by the five NN routes. Defaults: learning rate 0.05, momentum 0.8, 500 epochs, sigmoid, 1 hidden layer, 5 neurons per layer.
  • ID3 needs no context, because the server holds the tree and every ID3 page fetches what it needs.
  • Router location.state carries short-lived navigation payloads, such as the network shape passed to /nn_graph and the clicked node's id, layer and position passed to /node_info.

The three React Flow visualizations

  • Decision tree TreePage.tsx

    buildFlowFromJson walks the DTO in pre-order and gives each node a sequential id. Children are sorted by edge label so the layout is identical on every render. dagre is installed but unused: centerTreeLayout is a hand-written tidy tree that puts leaves in consecutive columns and centres each parent over its children.

  • Network topology NetworkGraph.tsx

    Built from the hyperparameters you chose: four labelled input nodes, hiddenLayers × neuronsPerLayer hidden nodes drawn as a custom orange σ node, and three output nodes. Edges are animated to suggest signal flow. Double-clicking a node parses its id into backend coordinates and opens its weights.

  • Island archipelago ViewIslandsPage.tsx

    Each island is a custom node: a half-dome with a sand-to-ocean gradient and three palm trees. Drag between handles to draw migration edges, chosen as unidirectional (grey) or bidirectional (red, two opposite edges). Edges live in IslandsContext, so they survive navigation.

Other frontend design choices

  • Deep-linkable drill-down. Clicking a tree node opens /node/:id. NodePage re-fetches /tree and repeats the same pre-order walk with the same child sort to find that node, so the URL alone rebuilds the view with no client state shared between pages.
  • One layout for every results page. A control row of buttons, a form row and a large monospace text area for backend output. ResultsPage.css is shared across algorithms.
  • Dataset viewers read static JSON. public/Datasets/*.json are JSON copies of the training and test files. TrainingExamplesTable loads several files in parallel with Promise.all, guards against setting state after unmount with a cancelled flag, keeps the JSON key order, and always puts Play last.
  • KaTeX for bit strings. HypothesisBreakdownPage uses \overbrace{101}^{\text{Outlook}} to label which attribute each run of bits encodes.
  • Theme. A dark slate and navy palette defined as CSS variables in index.css (--bg #0f172a, --panel #111827, --accent #60a5fa), with light cards on the hub page.

Algorithm 1 · Mitchell, Ch. 3

ID3 decision tree

ID3 builds a decision tree top-down and greedily. At each node it picks the attribute that best classifies the examples that reached it, using information gain, and it never backtracks.

The ID3 pages in use

Train on the 10-example set and check the rules and accuracy, open the tree and click into a node, then train on Mitchell's full 14-example table and watch the tree change. The clip is about a minute and loops while it is on screen.

  • Search strategy

    Greedy, top-down, hill-climbing through the space of trees. Each node commits to the highest-gain attribute among those still unused, and the choice is never revisited.

  • Inductive bias

    A preference for shorter trees, and for trees that put high-information-gain attributes near the root. The hypothesis space is complete (any function of the discrete attributes), so the bias comes from the search, not from a restricted space. This is Occam's razor.

What the UI shows

Implementation

Custom data structure: Node

public class Node {
   String name;                          // attribute tested here, or class label if leaf
   ArrayList<String[]> examples;         // training examples that reached this node
   HashMap<String, Node> children;       // attribute value -> subtree  (the branch label is the key)
   Node parent;                          // back-pointer (used for the empty-subset base case)
   String[] remainingAttributes;         // attributes still available below this node
   private boolean leaf;
   private StringBuilder rule;           // IF-THEN rule accumulated from root to this node
}
  • Children keyed by attribute value. Classification and DTO conversion follow branches by value directly, and each map key becomes the edge label in the UI.
  • Every node keeps its own example subset and remaining attributes. That is the data the node page shows, and why the visualizer can answer “which examples ended up here, and what could still be tested?”
  • Each node stores its own rule as it is built. Children copy the parent's rule prefix and append their own condition, and a leaf appends THEN <label>, so the rule exists the moment the leaf is reached. ID3tree.leafNodes collects the leaves, so there is no second traversal.
  • Parent pointer, needed only for Mitchell's “no examples left” case, which labels the leaf with the majority class of the parent.

The recursion ID3tree.java

findRoot(examples, attributes)
  choose best attribute A (by selected measure)
  root.name = A; root.rule = "IF A"
  partition examples by value of A        -> mapValues()
  create one child per observed value     -> setChildren()
  for each child: rule += " = v "; ID3(child)        (depth-first)

ID3(node)
  base case 1: all examples share a label   -> leaf(label)
  base case 2: no attributes remain         -> leaf(majority(node.examples))
  base case 3: no examples                  -> leaf(majority(parent.examples))
  choose best attribute among node.remainingAttributes
  map it back to its column in the original attribute array  -> updatedIndex()
  partition, create children with the reduced attribute list
  for each child: rule += "^ A = v "; ID3(child)
  • checkBaseCase returns a code (1 homogeneous, 2 no attributes, 3 empty, -1 continue) that ID3() handles with a switch.
  • Column re-indexing. Example rows are never copied or narrowed. Each node holds only a shrinking list of attribute names, and updatedIndex() translates a name back to its column in the original row, so example arrays are shared by reference across the whole tree.

Attribute selection, chosen by reflection

The measure in the request picks the statistic at runtime, with no switch to update: 

this.selectionMeasure = selectionMeasure + "Measure";   // "infoGain" -> "infoGainMeasure"
Method m1 = this.getClass().getDeclaredMethod(this.selectionMeasure,
                                              ArrayList.class, String[].class, Node.class);
return (int) m1.invoke(this, examples, attributes, node);

This is a lightweight strategy pattern by naming convention. A new criterion such as gain ratio only needs a method called gainRatioMeasure(...) and a new dropdown option.

MeasureChooses the attribute withFormula
infoGain (default)The maximum gain.Gain(S,A) = Entropy(S) − Σv (|Sv|/|S|)·Entropy(Sv)
entropyThe minimum weighted child entropy.Σv (|Sv|/|S|)·Entropy(Sv)

Entropy(S) = −Σ pi log2 pi is implemented in entropyHelper, with a hand-written logBase2(x) = ln x / ln 2 that returns 0 for x = 0 so the 0·log 0 term is defined. On the 10-example training set (6 Yes, 4 No) the starting entropy is about 0.971. Because Entropy(S) is the same for every candidate attribute at a node, the two measures always choose the same attribute. The toggle is there for teaching, since it shows both views of the same quantity.

From tree to rules, and rule-based classification

Mitchell §3.7 recommends turning a tree into one IF–THEN rule per root-to-leaf path, which is easier to read and is the first step of rule post-pruning. That conversion is how this implementation classifies.

  1. Rule extraction. /rules returns each leaf's rule, e.g. IF Outlook = Sunny ^ Humidity = High THEN No.
  2. Literal filtering (TreeUtils.processRules). Every token that is not an attribute value or class label seen in training is removed, leaving a compact precondition list such as Sunny High No.
  3. Classification (TreeService.calculateAccuracy). The rules form a decision list. For each test example, the first rule whose preconditions all appear in the example classifies it, and the prediction is correct if the rule's last token equals the label.

Rule post-pruning is not implemented. The About page explains it as a C4.5 extension: grow the tree fully, convert it to rules, drop preconditions that don't improve estimated accuracy, then sort the rules by accuracy. The backend builds the rule set that step would work on and already classifies with ordered rules, but it does not remove preconditions by validation accuracy. The filtering above only removes syntax tokens.

Algorithm 2 · Mitchell, Ch. 4

Neural network with backpropagation

A fully connected feed-forward network of sigmoid units, trained one example at a time by gradient descent on squared error with a momentum term (Mitchell §4.5, Table 4.2). Forward propagation, backpropagation, weight updates and activations are all custom code, with no TensorFlow or PyTorch.

The network pages in use

Train on Iris, read the accuracy report, change the number of hidden layers and train again, open the network graph, then double-click a neuron to see its learned weights.

  • Search strategy

    Stochastic gradient descent through weight space. The weights are updated after every training example, and momentum keeps the search moving in a consistent direction through small local minima and flat regions. It can still settle in a local minimum.

  • Inductive bias

    Mitchell's characterization is smooth interpolation: the network tends to label a new point like the training points around it. The hypothesis space is very expressive, so what you get is decided by the search, the starting weights (small, random) and when training stops.

What the UI shows

Output neurons have no outgoing edges, so the page handles them without a request and shows their classification label (Classification: Setosa, and so on).

The node page lists the neuron's outgoing connections and the weight on each one. Weights are stored on the sending neuron, so this view needs no extra bookkeeping: getNodeInfo(node) just pairs children[i].name with weights[i].

Implementation

Custom data structure: NeuralNode, an object per neuron with the weights stored on the sending neuron.

public class NeuralNode {
    String name;                        // "Input 1", "Hidden Layer: 1 Node: 3", "Output: 2"
    NeuralNode[] children;              // next layer (fan-out)
    double[] weights;                   // weights[k] = weight on edge this -> children[k]
    double[] previousChangeInWeights;   // delta-w from the previous update (momentum memory)
    double value;                       // activation o_j from the last forward pass
    double bias;                        // per-node bias, U(-0.5, 0.5)
    double previousChangeInBias;        // delta-b from the previous update (momentum memory)
    double error;                       // delta_j from the last backward pass
    SigmoidActivation activation;
}
  • setChildren(NeuralNode[]) creates the edges and allocates weights and previousChangeInWeights, one slot per child. All weights start uniform in [−0.5, 0.5), Mitchell's “small random values”.
  • Keeping the previous Δ on each node makes momentum local state. No separate gradient tensors are needed.
  • NeuralNetwork holds inputLayer (4), an ArrayList<NeuralNode[]> of hidden layers (any depth) and outputLayer (3). setupLayers creates and names the nodes, and connectLayers wires input → hidden1 → … → hiddenn → output.
  • ActivationFunction is an interface (activate(x), derivative(x)) implemented by SigmoidActivation.
sigma(x)  = 1 / (1 + e^(-x))
sigma'(o) = o * (1 - o)          // takes the already-activated output o (Mitchell's form)

Passing the activated value to derivative avoids computing exp a second time during backpropagation.

Forward and backward passes

Forward (feedForward), for each non-input unit j:
  net_j = b_j + sum_i( w_ij * o_i )      o_j = sigma(net_j)

Backward (calculateOutputError, calculateHiddenLayerError), Mitchell's Table 4.2:
  Output unit k:   delta_k = o_k (1 - o_k) (t_k - o_k)
  Hidden unit h:   delta_h = o_h (1 - o_h) * sum_{k in children(h)} ( w_hk * delta_k )

Hidden layers are processed from last to first, so each layer uses its children's δ values computed in the same pass.

Target encoding and prediction

  • One-hot targets. For a label c ∈ {0, 1, 2} the target is t_k = 1 when k == c and 0 otherwise, so each output neuron is a “class k detector”.
  • Prediction (makePrediction) is the argmax over the three sigmoid outputs (Setosa, Virginica, Versicolor).

Weight update with momentum updateWeights

Mitchell's momentum rule (eq. 4.18), applied after every training example.

delta_w_ij(n) = eta * delta_j * o_i  +  alpha * delta_w_ij(n - 1)
w_ij          = w_ij + delta_w_ij(n)

delta_b_j(n)  = eta * delta_j  +  alpha * delta_b_j(n - 1)        // hidden-layer biases

The previous Δ is saved on the node and reused as the momentum term in the next update. Momentum effectively increases the step size where the gradient is steady (Mitchell §4.5.2.1).

Decaying momentum (optional, off by default). The training loop passes the current epoch and total epochs into updateWeights(epochNumber, epochs), which computes decayValue = (epochs − epochNumber) / epochs as the basis for a linear schedule, αt = α0·(1 − t/T): high momentum early to move past flat regions, shrinking late so the weights settle without overshooting. The decayed-α line is commented out, so training uses a constant α.

Evaluation

  • Driver.testExamples runs every test row through makePrediction and builds a fixed-width report: Accuracy %, a Correct Predictions table (4 features, model prediction, actual class) and a Confusion Matrix section that lists every misclassified example, or “No misclassifications found!”.
  • On /nn_results, Train Network posts the hyperparameters, Check Accuracy fetches the report for the selected test file, and View Network opens the topology with the current shape.

Algorithm 3 · Mitchell, Ch. 9

Genetic algorithm, GABIL-style

The GA evolves a population of rule-set hypotheses for PlayTennis, each encoded as a bit string (Mitchell Table 9.1, the prototypical GA, and §9.3, GABIL). Fitness rewards accuracy and can penalize rule count. This implementation adds an island model: several populations with different selection, crossover and mutation settings evolve side by side.

Building an archipelago

Add islands with different settings (one uses the GABIL mutation extension), send the setup, step the evolution one generation at a time, open the islands, then click into a population and decode a hypothesis rule by rule.

  • Search strategy

    Stochastic and population-based, with no gradient. Selection keeps the fitter hypotheses, crossover recombines them, and mutation adds variation. Several islands search in parallel from different random starting points.

  • Inductive bias

    It comes from three places: the encoding (an ordered list of rules, each a conjunction of per-attribute disjunctions), the fitness (accuracy squared minus a rule-count penalty, so accurate and compact is preferred), and the operators, which decide what can be reached from where.

What the UI shows

Islands do not reproduce with each other. The edges are the migration topology you draw yourself. Red connections mean two islands directly swap individuals. Grey connections mean one island gives individuals to another while receiving from a different one.

The edges are stored in the browser but the backend does not read them yet. See known bugs.

Hypothesis encoding: 11-bit rules

Evaluator.getAttributeInformation reads the training file and builds an ordered value list per attribute, which gives a fixed 11-bit rule layout. A hypothesis is a variable-length int[] of k rules joined end to end (length 11·k).

  • Preconditions (bits 0 to 9) use one bit per attribute value. A 1 means the value is allowed. Several ones in one attribute block form a disjunction, a block of all ones means don't care, and a block of all zeros can never match.
  • Postcondition (bit 10) is the class index (0 = No, 1 = Yes).
  • Training examples use the same encoding (Evaluator.processExamples2): a one-hot bit for each attribute value and the class in slot 10. A rule matches an example when, in every attribute block, at least one bit position is 1 in both the rule and the example.

Strategy pattern throughout. Each genetic operator has an interface and an abstract base class holding a shared Random and helpers (flipBit, standardMutation, shouldMutate). Concrete classes are chosen per island from the DTO strings by factory methods, so any combination of operators can run on any island.

Fitness

accuracy(h) = (# training examples correctly classified by h) / |examples|
fitness(h)  = accuracy(h)^2  -  lambda * (#rules in h)          // #rules = |h| / 11
fitness(h)  = 0.001   if the above <= 0                          // floor ("zombie" sentinel)
  • Squaring the accuracy follows GABIL and sharpens selection pressure between hypotheses of similar quality.
  • λ, the rule-length penalty (per island, default 0.015), is the accuracy − λ·complexity trade-off. It works against rule-set bloat, which matters because variable-length crossover can make hypotheses grow.
  • Ordered classification. A hypothesis's rules are tried in order and the first match decides. An example no rule matches counts as incorrect.
  • The 0.001 floor keeps fitness positive for roulette-wheel selection. FitnessProportionalSelection also uses it as a sentinel and skips “zombie” hypotheses.

Initial population. AlgoTester.generateFirstGeneration(popSize) gives each individual 5 or 6 rules (50/50), with every bit set to 1 with probability ½. Each island draws its own, so the islands start from different points in the search space.

Selection strategies

UI valueMechanism
fitnessProportionate
backend fallback		FitnessProportionalSelection: roulette wheel (Mitchell eq. 9.1), P(h) = f(h) / Σ f, sampling with replacement and skipping zombies.
rankRankSelection: sort by fitness, descending. Rank i gets weight n − i, and sampling is over the total n(n+1)/2. Less dominated by a few elite individuals than roulette.
tournamentTournamentSelection(k = 3): draw 3 individuals at random (with replacement) and keep the fittest. k sets the selection pressure.
fitnessFitnessSelection: truncation, elitist. Deterministically take the top r by fitness.

Crossover strategies

UI valueMechanism
onePointSinglePointCrossover: pick one random point and swap tails.
twoPointTwoPointCrossover: pick two distinct points and swap the middle segments.
extendedTwoPointExtendedTwoPointCrossover: split both parents into [head, middle, tail] at the same two points. With 50% probability swap tails (and then, with another 50%, also swap middles). Otherwise swap only middles. That gives three kinds of offspring instead of one.
vary (default)VaryingRuleLengthCrossover: GABIL variable-length crossover, below.

Varying-rule-length crossover getSplits

  1. Choose two within-rule offsets d1 ≤ d2 in [0, 11).
  2. In parent A, choose rule indices r3 ≤ r4 and cut at r3·11 + d1 and r4·11 + d2.
  3. In parent B, choose its own rule indices r5 ≤ r6 but cut at the same offsets d1 and d2.
  4. Child A is A.head + B.middle + A.tail and child B is B.head + A.middle + B.tail.

Because both parents are cut at the same positions within a rule, every child is still a whole number of 11-bit rules with each bit in its correct field. Because they can be cut at different rule indices, children can have more or fewer rules than either parent. That is how the GA explores rule sets of different sizes, with λ pushing back against growth.

Mutation strategies

UI valueMechanism
standard (default)StandardMutation(rate): independent bit flips with probability mutationRate (default 0.01) per bit.
gabilGabilMutation(rate, addAlt = 0.0005, dropCond = 0.0001): per rule, a roulette choice between three operators weighted by their rates.
  • AddAlternative generalizes one attribute: within an attribute block it sets a random 0 bit to 1, adding a disjunct such as Sunny → Sunny or Rain. If every bit is already 1, the attribute is skipped.
  • DropCondition removes an attribute's constraint by setting its whole block to 1 (“don't care”).
  • Standard bit flip is used otherwise. With the default rates about 94% of rules get a standard flip, about 4.7% AddAlternative and about 0.9% DropCondition.

Varying-rule-length crossover, worked

A toy encoding keeps the numbers small: each rule is 5 bits (two attributes of 2 bits each, plus one class bit), where the app’s PlayTennis rules are 11 bits. Both parents have two rules. Parent A is cut after bit 1 and bit 8, which is d1 = 1 and d2 = 3 bits into its rules. Parent B must be cut at the same within-rule offsets, and the legal pairs of cut positions are (1, 3), (1, 8) and (6, 8). Here the pair (1, 3) is chosen.

One generation Island.evolve()

P  = current population (size = selectionRate + crossoverRate)

1. SELECT  S = selectionStrategy.select(P, selectionRate)     # survivors
2. SELECT  C = selectionStrategy.select(P, crossoverRate)     # parent pool
3. CROSS   O = repeatedly pick 2 random parents from C -> getOffspring(a, b),
              score each child; stop once |O| > |C|, then randomly
              discard until |O| == |C|
4. REPLACE P = empty
5. MUTATE  for s in S:  keep s unchanged with p = 0.75, else mutate + re-score
           for o in O:  ALWAYS mutate + re-score
           P = mutated S + mutated O

This follows Mitchell's prototypical GA, where (1−r)·p members survive and r·p are produced by crossover. Here both counts are set directly. With the UI defaults (selection rate 4, crossover rate 46, population 50) the population stays at 50 with a crossover fraction of 0.92. A survivor is only mutated 25% of the time, so most of the best individuals carry over intact.

The island model

  • Heterogeneous islands. Each IslandConfig sets its own selection strategy and rate, crossover strategy and rate, mutation strategy and rate, λ and population size. You can run tournament plus GABIL next to roulette plus two-point and compare them directly.
  • One generation per click. POST /ga/train runs exactly one evolve() on every island, sorts each population and prints each island's best bit string, its fitness and its training accuracy. Clicking Check Results repeatedly steps through evolution so you can watch convergence happen.
  • Rule pruning helper. AlgoTester.pruneRules(h, 11, examples) removes any rule that matches no training example. Such rules can never fire, so removing them does not change accuracy and lowers the λ penalty. It is implemented but not yet called in the generation loop.

User flow

  1. On /ga_results, fill in Island Settings and click Add Island. The form resets to defaults and a read-only card for the island appears, newest first. Repeat to build an archipelago.
  2. Send Train POST calls POST /ga/setupIslands with every island's configuration, which creates each initial population.
  3. Check Results calls POST /ga/train, which runs one generation and reports each island's best hypothesis, fitness and accuracy.
  4. View Islands opens the React Flow archipelago, where you can draw migration edges.
  5. Double-clicking an island opens /island/:id, which lists the live population from getPopulation, sorted best first.
  6. Hypothesis Breakdown opens a three-column view: the rules on the left, a carousel (Prev and Next, wrapping around) that shows the selected rule's bits and its decoded IF–THEN sentence in the centre, and a KaTeX-annotated sample rule on the right as a key to the encoding.

Known bugs and where it stands

I stopped working on this project. I got bored of it and moved on to the reinforcement-learning algorithms instead, so the bugs below were never fixed. They are recorded here so the list is honest, and as a guide for anyone who wants to pick it up.

ID3

  • processRules removes syntax tokens from rules but does not prune preconditions by validation accuracy, so rule post-pruning is missing.
  • Attribute names are fixed to the PlayTennis schema in TreeService.attrs, so other datasets would need code changes.

Neural network

  • train() sets a local epocs = 300, which overrides the epochs you send.
  • The frontend sends epochs and activation, but NetworkRequest expects epocs and activationFunction, so those two settings never reach the backend. Learning rate, momentum, hidden layers and neurons per layer do bind correctly. The Tanh, ReLU and GELU options in the dropdown are not implemented either way.
  • Output-layer biases are initialized but never updated.
  • Features are not normalized, and training examples are not shuffled between epochs.

Genetic algorithm

  • The backend always loads Tennis-Train.txt and ignores trainFile and testFile from the request.
  • SinglePointCrossover and TwoPointCrossover assume both parents have the same length, but the initial population mixes 5-rule and 6-rule hypotheses. They also change the parent arrays in place, which can alter survivors that were selected into both pools. The other two crossovers work on copies and don't have this problem.
  • Migration edges are drawn in the UI but never sent to the backend, so islands evolve independently. /ga/getHypothesisStats is a placeholder that returns “Coming Soon”.

Platform

  • Models are held in server memory (a singleton and static fields), and System.out is swapped globally during training. The app is single-user: concurrent training requests would interfere with each other.
  • The Dockerfile copies only pom.xml and src/. ID3 data is on the classpath and works in the container, but the NN and GA data files in Backend/ would need to be copied in, or moved to resources/.
  • The frontend's API base (http://localhost:8080) is hard-coded on each page. A Vite environment variable (import.meta.env.VITE_API_URL) would make deployment easier.
