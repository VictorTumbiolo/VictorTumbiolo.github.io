    The problem: Overcooked

    Overcooked-AI (Carroll et al., 2019) is a cooperative gridworld based on the Overcooked video games. Two chefs share a small kitchen and produce as many soups as possible before time runs out.

    Making one soup

    1. Pick up an onion from a dispenser and drop it in a pot.
    2. Repeat until the pot holds three onions. It then starts cooking on its own.
    3. Pick up a dish, collect the finished soup from the pot with it, and carry it to the serving window.

    Setup used here

    Agents2, fully cooperative, shared goal
    RecipeSingle recipe, 3 onions (the *_o_1order style layouts)
    Episode length400 timesteps (fixed horizon)
    Actions6, discrete: up, down, left, right, stay, interact (pick up / place / deliver)
    Observation96-dimensional featurized vector per agent (featurize_state_mdp): object locations, both agents' positions, pot and soup progress
    Sparse reward+20 per delivered soup, shared by both agents

    What makes it interesting

    • Sparse reward

      A soup is only worth +20 once a full sequence of steps is done, so the agents have to discover the whole pipeline: onions, pot, dish, pickup, delivery.

    • Coordination

      Both chefs share counters, pots and walkways. Good play means staying out of each other's way and splitting the work.

    • A changing partner

      From one agent's point of view the other agent is part of the environment, and it is learning at the same time. Centralized training is aimed at exactly this.

    The algorithm: MAPPO

    MAPPO is PPO adapted to cooperative multi-agent problems using centralized training, decentralized execution (CTDE).

    • Actor Decentralized

      Takes only an agent's own 96-dim observation and outputs a distribution over the 6 actions. That is all that's needed at execution time, so the agents need no communication.

    • Critic Centralized, training only

      Sees the joint state, both observations concatenated into a 192-dim vector, and estimates the value. Conditioning on both agents gives the learning signal a full view of the kitchen.

    • Parameter sharing

      One actor network is shared by both agents, each feeding in its own observation. Both chefs have the same abilities, so a single policy can play either role.

    • PPO core

      Clipped surrogate policy loss, value loss, entropy bonus, and Generalized Advantage Estimation (GAE).

    Why MAPPO

    It was chosen over independent PPO because the centralized critic accounts for the other agent when estimating value, and over value-decomposition methods like QMIX because Overcooked's coordination comes from sequential interaction over shared resources rather than value that factors neatly across agents.

    Network model.py

    Actor:   obs (96)          -> Linear 256 -> ReLU -> Linear 128 -> ReLU -> Linear 6   (action logits)
Critic:  global state (192) -> Linear 256 -> ReLU -> Linear 128 -> ReLU -> Linear 1   (value)

    Update step PPO_Agent.py

    Run after every 400 environment steps, which is one full episode.

    1. Collect the rollout buffer: local obs, global state, actions, old log-probs, rewards, values and done flags.
    2. Compute GAE advantages, and value targets as advantage plus value.
    3. Normalize advantages to zero mean and unit variance.
    4. Run 3 gradient epochs over the batch, minimizing L = L_clip + 0.5 * L_value - ent_coef * entropy with the policy ratio clipped to [1 - 0.2, 1 + 0.2].
    5. Decay the entropy coefficient and clear the buffer.

    Parameters and design choices

    Hyperparameters

    ParameterValue
    OptimizerAdam, learning rate 3e-4
    PPO clip0.2
    Discount (gamma)0.99
    GAE lambda0.95
    Value loss coefficient0.5
    Entropy coefficientStarts 0.05, multiplied by 0.9995 each update, floor 0.001
    Update frequencyEvery 400 environment steps (one full episode)
    Gradient epochs per update3
    Training length5,000,000 environment steps per layout (about 12,500 episodes)
    DeviceCPU, roughly 1.5 hours per layout

    Reward design

    Shaped rewards supplement the sparse delivery reward to guide the agents through the soup pipeline.

    EventRewardReasoning
    Soup delivered+20 sparse, sharedHighest value, so completing soups is the priority.
    Onion placed in pot+5 shaped, per agentHappens about 3 times per soup, so it is weighted above dish pickup.
    Soup picked up+6 shaped, per agentRewards the handoff from cooking to delivery.
    Dish picked up+2 shaped, per agentKept small so it guides behavior without becoming a goal of its own.
    Every timestep−0.001 per agentMild pressure to be efficient.

    The sparse reward is shared to keep the agents cooperative, while shaped rewards are credited per agent (shaped_r_by_agent) to give each one localized feedback about what it did.

    Other design choices

    • Exploration comes from sampling the stochastic policy plus the entropy bonus, which decays over training. No extra action noise is added.
    • Checkpointing. A 100-episode running average of soups delivered is tracked during training, and the checkpoint with the best running average is saved and used for evaluation.
    • One model per layout, with identical algorithm, reward structure and hyperparameters, so differences between layouts come from the environment rather than the tuning.
    • Local-only actors at test time. Each chef uses only its own observation. The critic is only used in training.

    Training and evaluation

    Coordination and efficiency metrics

    Observations

    • Learning curves share the same shape: zero soups at first, a sharp rise once a successful trajectory is found, then a plateau. Cramped Room converges fastest, then Coordination Ring, then Counter Circuit, which has the largest state space.
    • Cramped Room is the most consistent, with zero variance across 100 games. The small space leaves one clear way to play.
    • Coordination Ring has the highest throughput. Its symmetric layout lets both chefs run the whole pipeline, and both pots get used.
    • Counter Circuit shows emergent division of labor: one agent tends to run the pots while the other supplies ingredients. Nothing in the environment forces this.
    • Efficiency. Pickups per soup are about 1.0 in every layout, so the path from cooking to delivery is nearly lossless, and almost no soups are dropped. Potting per soup stays close to the 3 onions a soup requires.

    What each file does

    Everything lives in the MAPPO/ folder.

    Core

    model.pyDefines SharedActorCritic, the network used by both agents: a shared-weight actor (96 → 256 → 128 → 6 action logits) and a centralized critic (192 → 256 → 128 → 1 value).
    PPO_Agent.pyThe PPO update logic MAPPO is built on. PPOUpdater runs GAE advantage estimation, the clipped policy loss, value loss, and decaying entropy bonus. RolloutBuffer stores each step's local obs, global state, action, reward, log-prob, value and done flag.
    Driver_W_Save.pyThe training script. Builds the environment for a chosen layout, steps both agents with the shared actor, applies the shared sparse reward plus per-agent shaped rewards and time penalty, triggers a PPO update every 400 steps, writes a training log, and saves the model whenever the 100-episode running average hits a new best. Set the layout in main().

    Evaluation and visualization

    Agent_Test_Visual.pyLoads a trained model, plays one episode with both agents, prints the reward and soup count, saves the episode as an .mp4, and then replays it in a pygame window. Choose the layout and model by setting MODEL_PATH and LAYOUT at the top.
    100_window_metric_test.pyRuns 100 evaluation episodes for a trained model and records soups delivered, optimal onion potting, soup pickups and soup drops. Writes a per-episode metrics file and a summary file (average, totals, std dev, min, max) to testing_logs/.
    Save_All_Videos.pyLoops over every layout shipped with Overcooked-AI and saves a PNG of each one's starting state to layout_images/, sized to that layout. These are the images in the belt above.

    Charts

    DISPLAY_TRAINING_RESULTS.pyPlots the 100-episode running average of soups for each layout from the training logs on one chart, marking each layout's peak. The log paths are listed in the files list at the top.
    DISPLAY_TESTING_RESULTS.pyPlots soups delivered per evaluation episode for each layout from the per-episode metrics logs. The paths are listed in the files dict at the top.
    METRIC_CHARTS.pyDraws the bar charts of optimal potting and soup pickups per layout, both as absolute averages and normalized per soup delivered. Values come from testing_logs/metrics_compiled.txt.

    Data folders

    models/Trained weights (.pth), one per layout: cramped_best_model.pth, ring_best_model.pth, counter_circuit_best_model.pth.
    training_logs/Per-episode training logs for each layout, with columns for episode, average reward, soups, and the 100-episode running average.
    testing_logs/Per-episode and summary results from the 100-episode evaluations for each layout, plus metrics_compiled.txt combining the headline numbers.
    charts/Generated figures.
