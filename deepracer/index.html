AWS DeepRacer, Written as Code

A simulated 1/18-scale race car learns to drive laps from nothing but two camera images and a LiDAR scan. The agent is a Soft Actor-Critic written from scratch in PyTorch, and it talks to a patched DeepRacer simulator running in Docker. Everything the DeepRacer console hides behind a Train button is code here.

The problem: drive fast, from sensors only

A simulated race car must drive laps around a closed track, as fast and as reliably as it can, using only what its sensors show it. It is never told where it is, which way it faces or how fast it is going, so the problem is partially observable.

ObservationsTwo grayscale stereo camera images (120×160 each) and a 64-beam 360° LiDAR scan. No position, heading, speed or map.
ActionsA continuous 2-vector: steering angle in [−30°, +30°] and speed in [0.5, 0.7] m/s. The policy outputs values in [−1, 1] and the simulator scales them.
RewardComputed by a user-written function from privileged simulator state (progress, distance_from_center, all_wheels_on_track, is_crashed, …). The agent never sees that state, only the resulting number.
Episode endsTerminated on lap complete, crash, leaving the track or reversing. Truncated on time-up or when the car is immobilized.
GoalOne policy that completes laps on several different tracks, not one policy per track.
Race typesTime-Trial, Obstacle Avoidance (6 static obstacles) and Head-to-Bot (3 bot cars). The environment config supports all three. The agent work here is on Time-Trial.

What makes it hard

  • Expensive data

    Pixel input and a single, non-vectorizable simulator, so every transition is collected one at a time.

  • Different tracks

    Layouts with very different geometry, from wide sweepers to tight corners.

  • Exploitable reward

    A shaped reward is easy for an agent to game instead of actually racing.

  • Forgetting

    Fine-tuning on a new track tends to make the policy forget the old one.

How this differs from the DeepRacer console

The AWS DeepRacer console is a configure-and-click product. You pick a track and sensors, define an action space, write a reward function, adjust a few hyperparameters and press Train. The learning algorithm, the network and the training loop are fixed and hidden behind the interface.

This project removes that layer. The simulator is the same, but everything the console hides is now code.

In short, the console is a settings panel for someone else's algorithm. This is an RL research workspace where the algorithm, the network, the data pipeline and the experiment design are all code. agent_params.json keeps the console's model_metadata.json format because the simulator still reads it, but its neural_network field is inherited and doesn't affect the custom network.

The algorithm: Soft Actor-Critic

SAC is an off-policy, maximum-entropy actor-critic method for continuous control. It maximizes expected return plus a policy-entropy bonus. 

J(pi) = E[ sum_t r_t + alpha * H(pi(. | s_t)) ]

Why SAC here

  • Sample efficiency

    The simulator is one slow, non-vectorizable instance. Off-policy replay reuses every transition many times, which PPO can't.

  • Built-in exploration

    The entropy term keeps the policy stochastic, which matters when one policy must cope with several track shapes.

  • Stable value learning

    Twin critics with a min-target reduce overestimation bias. Soft target updates smooth the TD targets.

  • Less tuning

    The entropy temperature α is learned automatically toward a target entropy.

Components sac_agent.py run.py

PolicySquashed Gaussian. The actor outputs mean and log_std (clamped to [−20, 2]) and samples with the reparameterization trick, a = tanh(mean + std·ε), correcting the log-probability for the tanh squash.
Deterministic modea = tanh(mean), used for evaluation and for rendering the laps above.
CriticsTwo Q-networks, each [feature(128) + action(2)] → 256 → 256 → 1 with ReLU.
TargetsTarget copies of both critics, updated by Polyak averaging with τ = 0.005.
TD targety = r + γ(1 − done)·( min(Q1', Q2')(s', a') − α·log π(a'|s') )
Critic lossMSE(Q1, y) + MSE(Q2, y)
Actor lossE[ α·log π(a|s) − min(Q1, Q2)(s, a) ]
TemperatureA learned log_alpha with loss −log_alpha · (log π + H_target).
Target entropyaction_dim × target_entropy_scale = 2 × (−0.5) = −1.0
OptimizersThree Adam optimizers: actor, critic (plus encoder) and α.
Gradient clippingNorm 0.5 on the Q1, Q2 and actor parameters.
Replay bufferA circular numpy buffer of flattened observations, actions, rewards, next observations and done flags.

Design choices worth knowing

  • The encoder is trained by the critic loss only. The actor receives detached features, so policy gradients never reach the encoder. This keeps the shared visual representation stable.
  • One shared encoder, with a LayerNorm and a 128-d feature head after it. Actor and critics read the same 128-d feature.
  • Random warmup. The first 1,000 steps use uniform random actions. In the fine-tuning runs, warmup uses the pretrained policy instead, so the buffer isn't filled with random driving before gradient updates start.
  • Batched, delayed updates. The loop collects update_steps transitions, then runs updates_per_step gradient steps in one burst, instead of one update per environment step.
  • NaN guard. If a sampled action contains NaN, the run stops and dumps the encoder statistics, mean, log-std and α.
  • Checkpointing. A checkpoint is saved after two consecutive completed laps (progress at least 99.5%). Fine-tuning runs also save every 2,500 steps, which allows model selection afterwards.

Network and sensors

Which sensors the agent uses

The platform offers more sensors than the agent needs. agent_params.json selects ["STEREO_CAMERAS", "LIDAR"].

  • Stereo cameras

    Two forward 120×160 grayscale images. They capture track edges and curvature, and the left and right pair provides depth cues.

  • LiDAR

    64 radial distances over 360°. Short-range proximity for walls, obstacles and bots, and it covers what the cameras can't see behind and beside the car.

Not available to the policy: the car's x/y position, heading, speed, distance from the centerline, track progress or waypoints. These exist inside the simulator and are visible only to the reward function.

Observation layout and pre-processing

[ LIDAR (64) | STEREO_CAMERAS (2 x 120 x 160 = 38,400) ]   ->   38,464 floats
  • LiDAR: nan_to_num (NaN to 0, +inf to 1, −inf to 0), then clamp to [0, 1]. This works because the simulated max range was patched to 1.0 m.
  • Cameras: divide by 255 to get [0, 1].

Encoder transforms.py

Stereo camera encoder (-> 96-d)
  left / right (1x120x160)
    -> Conv2d(1->16, k4, s2) -> LeakyReLU -> Conv2d(16->8, k4, s2) -> LeakyReLU   shared per-eye encoder
    -> concat along channels (16x28x38)
    -> Conv2d(16->16, k4, s2) -> LeakyReLU -> Conv2d(16->64, k4, s2) -> LeakyReLU stereo fusion
    -> flatten (2,560) -> Linear 96 -> LeakyReLU

LiDAR encoder (-> 32-d)
  (1x64) -> Conv1d(1->16, k4, s2) -> LeakyReLU -> Conv1d(16->16, k4, s2) -> LeakyReLU
         -> flatten (224) -> Linear 32 -> LeakyReLU

Fusion
  concat(camera 96, lidar 32) = 128 -> LayerNorm(128) -> Linear(128->128) + ReLU

Weights use orthogonal initialization (gain √2, bias 0.01). The activation is LeakyReLU in the encoders and ReLU in the heads.

Heads

actor:   128 -> 256 -> 256 -> [mean(2), log_std(2)]
critic:  (128 + 2) -> 256 -> 256 -> 1        (x2, plus 2 target copies)

Reward function reward_function.py

Evaluated every step on the simulator's reward_params.

if is_crashed:                 reward = -1.0
if not all_wheels_on_track:    reward = 1e-3
centering = 1.0 if dist <= 0.10 * width
            0.5 if dist <= 0.25 * width
            0.1 if dist <= 0.50 * width
            else return 1e-3
progress_reward = sqrt(progress / 100)
reward = 0.2 * centering + 0.8 * progress_reward
  • The square root of progress is concave. It pays relatively more for early progress, so the agent isn't indifferent between "almost there" and "just started".
  • Centering is a coarse three-level band. It is a small tie-breaker (20%) and doesn't dominate speed or progress.
  • The crash penalty (−1) is the only negative reward. Everything else is positive, so surviving always beats ending the episode early.
  • An earlier variant with milestone bonuses at 25, 50, 75 and 100% progress is kept in comments. The final version dropped them and added the crash penalty.

The three tracks

All three are layouts bundled with the simulator, selected by WORLD_NAME.

TrackSimulator worldCharacterTypical lap
A to Z SpeedwayreInvent2019_wideWide lanes, sweeping curves. Forgiving, and it rewards smooth high-speed driving.~375–400 steps
Smile SpeedwayreInvent2019_trackNarrower, with tighter turns. Needs precise low-speed maneuvering.~535 steps
AWS Summit RacewayVegas_trackLonger and more complex, a mix of straights and corners. The most difficult track overall.~500–515 steps

AWS Summit Raceway is the most difficult of the three. A to Z is wider and more forgiving, and Smile asks for precise low-speed cornering where the other two reward speed. That conflict is part of why a single policy struggles to be good at all three.

The track is changed by editing WORLD_NAME in environment_params.yaml, or by passing -W <world> to the restart script. The simulator must restart for it to take effect. Start positions are randomized and the driving direction alternates, which stops the agent from memorizing one start.

Training strategy and results

1. Single-track pretraining on A to Z

The 100-episode average progress rose from about 10% at 5k steps to over 80% by about 45k steps. α decayed from about 0.93 to 0.05.

2. Checkpoint selection on an unseen track

Candidates were evaluated on Smile Speedway, which they hadn't trained on.

Over 50 episodes, step 28,030 completed more laps (42 against 34) with lower variance than 28,904, so it became the base for later training. The longest-trained checkpoint (97,499) generalized worst.

3. Forgetting, and the multi-track fix

Fine-tuning on a single new track led to catastrophic forgetting. After training only on AWS Summit Raceway, the same model completed only 4 of 10 laps on A to Z Speedway.

The fix was a multi-track curriculum: tracks are re-drawn by weighted random sampling every 2 episodes, the container restarts into the chosen world, and training continues from a pretrained checkpoint on one shared replay buffer. That produced the strongest overall model, 14008_post_multi_train. A later targeted fine-tune on Smile (lower learning rate, pretrained-policy warmup, 75% sampling weight) gave mixed results.

Lessons and caveats

  • Forgetting against dilution. Sequential training forgets earlier tracks. Mixed training avoids that, but one replay buffer and one critic must then represent very different dynamics, and the wide-track experience can drown out the transitions Smile's tight corners need.
  • Entropy creep during fine-tuning. The automatic α tuning that helps from scratch can raise α again during fine-tuning, adding action noise just when the policy should tighten up. Freezing α, or using a much smaller alpha_lr, is the likely fix.
  • Fine-tuning is sensitive to warmup and learning rate. Starting updates from a buffer of random actions at a high learning rate degraded pretrained policies quickly. Filling the buffer with the pretrained policy first, at a lower learning rate, was much more stable.
  • Single-frame observations. There is no frame stacking and no recurrent state, so the policy can't directly infer velocity. Speed is only partly recoverable from the images.
  • Possible improvements. Per-track replay buffers, a track-conditioned policy or separate encoder heads, longer and more gradual curricula, and domain randomization over width and curvature.
  • Simulation to reality. The simulated cameras are noise-free and evenly lit, and the LiDAR is idealized. Transfer to a physical car would need noise, lighting and physics randomization.

The Docker simulator

The simulator is not a Python library. It is a ROS Melodic and Gazebo 9 application (Python 3.6, with a Coach-style RL stack) that a container exposes through a ZeroMQ socket on port 8888. The Python side runs on your machine as a normal Gym environment that talks to that socket. 

host (your Python venv)                     Docker container
------------------------                    ----------------------------------
run.py / visual.py / eval*.py               Gazebo + ROS Melodic (DeepRacer sim)
  gym.make('deepracer-v0')                    patched gym_agent (ZMQ REP server)
    DeepracerGymEnv                             sends obs and info,
    DeepracerGymAdapter  --- ZMQ REQ --->        receives actions
    reward_function(info['reward_params'])      configs/ mounted read-only
                              port 8888

Image layers

  1. Base image. A prebuilt DeepRacer simulation image from Docker Hub (tag v0) with ROS, Gazebo, the track worlds and the training stack. It's large, about 5 GB compressed and 19 GB on disk, and is downloaded once.
  2. Dockerfile. Layers this project's patches on top (the patches/ directory is copied into the image):
    • Camera path fix. Corrects a hard-coded Gazebo model name so the camera topics resolve.
    • Info-dict patch (environment_response.py). Injects reward_params and episode_status into every step's info. This is what lets the Python side compute the reward and read progress, lap_complete, crashed, reversed, off_track, immobilized and time_up.
    • Kinesis video streaming disabled, so the sim doesn't try to stream to AWS.
    • LiDAR range raised from 0.5 m to 1.0 m, in every file where it's defined.
    • gym_agent.py. Replaces the stock PPO agent with a pass-through that binds a ZMQ REP socket on port 8888. It sends each observation (msgpack with numpy support) and applies whatever action comes back, and it handles resets with dummy actions.
    • launch-simapp-rosnodes.sh. A custom launcher that reads /configs/environment_params.yaml, builds the simulator's parameter file, copies agent_params.json in as the model metadata, and starts the simulation under a virtual display (Xvfb) with roslaunch.
  3. deepracer.def. The same patches as an Apptainer definition, for machines without Docker such as shared HPC clusters, where ports are derived from a hash of the username so users don't collide.

Scripts scripts/

start_deepracer.shPulls the base image if missing, builds the patched deepracer image if missing, then runs the container detached on port 8888 with configs/ mounted read-only (3 CPUs and 6 GB by default). Options: -C CPUs, -M memory, -E true evaluation mode, -W <world> track for evaluation. With Apptainer it builds and starts a .sif instance instead.
stop_deepracer.shStops the container (Docker) or the instance and overlay (Apptainer).
restart_deepracer.shStop, then start, passing the options through. This is how the track is switched mid-experiment.
cleanup_deepracer.shFull teardown. Removes the container and deletes the images, forcing a full re-download. Also removes a Conda env named deepracer if one exists. Use only for a clean slate.

Heads-up on cleanup: after a fresh image build, start_deepracer.sh runs docker system prune --force. That prunes dangling images, stopped containers, unused networks and build cache across the whole Docker host, not only DeepRacer's. If you share the host with other projects, back up what you need first or remove that line.

Training mode and evaluation mode

  • Training mode (default). The track comes from WORLD_NAME in environment_params.yaml.
  • Evaluation mode (-E true -W <world>). The track comes from the -W argument and ignores the YAML, which makes sweeping several tracks scriptable. The evaluation helpers call restart_deepracer.sh this way before each track.

The client protocol packages/deepracer_gym/

zmq_client.pyA ZMQ REQ socket with msgpack serialization. The first connection has a long timeout (about 8 minutes, because the sim takes a while to boot), then a shorter one (about 100 s).
gym_adapter.pyTranslates between Gym semantics and the sim's request/response loop. After an episode ends it sends dummy actions until the sim confirms the next one has started, and it maps the sim's flags to Gymnasium's terminated and truncated.
envs/deepracer_gym.pyThe deepracer-v0 environment. Observations come from the sim, the reward is computed locally from info['reward_params'], and the action space is Box(−1, 1, (2,)).
src/utils.pymake_environment() wraps the env with FlattenObservation and RecordEpisodeStatistics. It also holds the multi-track evaluation helpers.

Running it

  1. Start Docker. On Windows, run the bash scripts from WSL and enable Docker Desktop's WSL integration for that distro.
  2. From the project root, run the start script. The first run downloads the base image and builds the patched one (several minutes), and the sim needs another 30 to 120 seconds to boot before it answers on port 8888.
  3. In a Python environment with the dependencies installed (gymnasium, torch, pyzmq, msgpack, msgpack_numpy, imageio, loguru, munch, pyyaml, …) and the project and packages on the Python path, run a script.
bash scripts/start_deepracer.sh

What each file does

Run Python files as modules from the project root (python -m src.<name>). Several scripts keep their settings (checkpoint path, episode count, output folder) as constants at the top, so check those first. Scripts that switch tracks edit environment_params.yaml and restart the simulator, so run only one at a time.

Agent and learning components src/

sac_agent.pyThe SAC agent used by all training and evaluation. Defines the shared encoder with LayerNorm and feature head, the actor, twin critics and target critics, the learned temperature α, observation pre-processing, action sampling with the tanh log-probability correction, and soft target updates.
transforms.pyThe observation encoders: a stereo-camera CNN (a shared per-eye CNN, then a fusion CNN) and a 1-D CNN for LiDAR. EncodeObservation splits the flat vector back into LiDAR and camera parts and concatenates their encodings. Also holds the orthogonal-init helper and identity pre-processing stubs.
agents.pyA base Agent class, a RandomAgent baseline, and a second copy of SACAgent. Training and evaluation scripts use the one in sac_agent.py.
replay_buffer.pyCircular numpy replay buffer that samples random minibatches as torch tensors.
utils.pySeeding and device selection, make_environment(), reading the world and race type from the config, demo() for recorded videos, evaluate() and evaluate_track() for multi-track evaluation, box-plot generation and the lap-time helper.

Training scripts

run.pyThe main single-track SAC loop, from random weights. Handles random warmup, batched update bursts, TensorBoard and text logging, and saves a checkpoint after two consecutive completed laps plus a final model.
run_curriculum.pyThe same loop, but loads a pretrained checkpoint first. Uses hyper_params.yaml as is and saves periodic checkpoints every 2,500 steps, on whichever track the config names.
multi_track_train.pyMulti-track curriculum. Starts from a pretrained checkpoint, samples a track by weight every 2 episodes, rewrites WORLD_NAME, restarts the simulator and keeps training on a shared replay buffer. Random-action warmup, verification GIFs for the first episodes, and checkpoints on consecutive laps of a chosen track.
multi_track_eval_detministic_warmup.pySame as multi_track_train.py, except warmup uses the pretrained policy instead of random actions. The more stable way to fine-tune. Despite the name, it is a training script.
htb_train.pyHead-to-bot fine-tuning from a pretrained model, with periodic checkpoints. The bot count is set in environment_params.yaml.
htb_multi_track_train.pyHead-to-bot training across all three tracks with near-equal weights (0.34, 0.33, 0.33), switching every 2 episodes.

Evaluation and visualization

batch_eval.pyEvaluates every .torch file in a folder on the configured track and writes a table of min progress, std dev, laps and episodes above 50%. This is how the best checkpoints were picked.
all_tracks_eval.pyEvaluates one checkpoint on all three tracks in turn, switching the track and restarting the simulator each time. Writes a summary file.

visual.pyRuns one episode with a chosen model and saves a GIF. Options: --model, --output, --max-steps, --fps, --frame-skip, --deterministic. These are the lap videos above.

Settings configs/

agent_params.jsonSensors, action-space bounds (steering ±30°, speed 0.5–0.7 m/s), continuous action type, and the inherited console fields. Read by both the Python environment and the simulator. Changing the sensors changes the observation size, so saved models would no longer match.
environment_params.yamlSimulator and race settings: WORLD_NAME, obstacle and bot counts, bot speed, start-position randomization, driving direction, lane changes and domain randomization. The container reads it at startup, and the multi-track scripts rewrite it automatically.
hyper_params.yamlThe SAC hyperparameters. Currently set for fine-tuning (learning rate 3e-5), so raise them for training from scratch.
reward_function.pyThe reward, called every step. The active version mixes a three-level centering score (20%) with the square root of progress (80%), gives −1 for a crash and 0.001 off the track.
