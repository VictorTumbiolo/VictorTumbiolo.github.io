Naive RAG

A chat-with-your-paper web app. Upload an academic PDF, and Claude answers questions by retrieving only the relevant passages instead of reading the whole paper. It is naive on purpose: a brute-force, heuristic baseline that I am improving one design choice at a time, with each change tested before it goes into the app.

Work in progress. This project is being actively changed, and I am currently testing rerankers, which is taking quite a bit of time. Everything here describes the app as it stands today, and several choices below are placeholders that are waiting on those tests.

Not currently hosted. The app used to be live, with the frontend on Vercel, the backend on Railway and the vectors in Qdrant Cloud. I have taken it down for a brief period while I make rapid updates, since the design is changing too often to keep a deployment in step. It still runs locally (see Running it), and it should come back once things settle.

What it is

The app is built for students and researchers. A user uploads an academic PDF, the backend splits it into chunks and embeds them into a vector database, and Claude answers questions by retrieving only the passages that matter. The goal is lower token usage than a normal chatbot session while keeping answers grounded in the paper.

It takes one paper at a time for now, and caps uploads at 15 pages. The interface shows a PDF viewer, a chat panel and a paper list, and each answer reports how many tokens the retrieval used and how many it saved against sending the whole paper.

The app

The main screen is a PDF viewer on the left and a chat panel on the right, with a collapsible paper list. The viewer is resizable, and the app loads a sample paper on first visit so there is something to try.

Asking a question

Claude isn't forced to search. It is given a single tool, search_paper(query), and decides whether to use it. A follow-up like “explain point 2” should skip retrieval, while a question about the paper's content triggers a search with a rewritten, standalone query.

The answer is written from whatever the search returned, and markdown renders in the chat bubble. The backend keeps the last 5 exchanges of the conversation for context.

Token savings, shown on every answer

Below each answer is a one-line summary, with a tooltip that explains it. Tokens used is the size of the passages retrieved to answer the question. Saved is the difference between that and the paper's total token count, which is roughly what a full-paper approach would have cost.

In the example shown, the answer used 4,301 tokens out of a 12,419-token paper, which saved 8,118. That is one run, and it lands a little above the 33% budget because the selection stops once the running total reaches the budget, so the last chunk can overshoot it.

Why “naive”

“Naive RAG” is the plain recipe: chunk, embed, top-k vector search, stuff the results into the prompt, generate. This app follows it with simple heuristics, some of them brute force, on purpose. It is a baseline, not a finished design.

The method is to improve it one design choice at a time. Each change is tested on its own in an offline harness, and only then folded back into the app, instead of redesigning everything at once. That keeps every improvement attributable to a single decision.

Architecture

A React single-page app talks to a FastAPI backend, which holds the RAG pipeline and talks to Qdrant and the Anthropic API.

Ingestion POST /papers

  1. The user uploads one or more PDFs, then clicks Chunk PDF.
  2. The backend skips any file whose filename already has chunks in Qdrant (already_chunked).
  3. It rejects PDFs over 15 pages (rejected_too_long), and the frontend says to limit them to 15 pages or less.
  4. It extracts the text with PyMuPDF and splits it with RecursiveCharacterTextSplitter (800 characters, 100 overlap).
  5. It embeds each chunk with all-MiniLM-L6-v2, counts each chunk's tokens with Anthropic's count_tokens, and upserts to Qdrant with a payload of {filename, chunk_index, text, tokens}.

Question POST /ask

  1. The frontend sends the question, the filename and the chat history, and the backend trims the history to the last 5 exchanges.
  2. Claude has one tool, search_paper(query), and decides whether to search.
  3. retrieve_chunks() embeds the query and pulls up to 500 candidate chunks filtered to that filename. It then walks them in similarity order until the running token total reaches 33% of the paper's total.
  4. The chunks are joined with --- separators and returned to Claude as the tool result, and Claude writes the answer.
  5. The response includes tokens_used and total_tokens, which the UI shows as Tokens used, Saved and Total.

The frontend and backend API

The base URL comes from VITE_API_URL. CORS allows http://localhost:5173 and the Vercel origin the app used to run on.

EndpointMethodRequestResponse
/papersPOSTmultipart/form-data with a repeated files field of PDFs{ papers: [{ filename, num_chunks, status, page_count? }] }, where status is chunked, already_chunked or rejected_too_long
/askPOSTJSON { question, filename, history: [{role, text}] }{ received, searches[], searched, tokens_used, total_tokens }
/testPOST{}{ "test": "test" }, a health check that separates backend problems from Qdrant Cloud or Claude API problems. It is behind the Test button.
  • Errors. /ask returns 400 on an empty question and 500 on any pipeline failure, and the UI says “Something went wrong reaching the backend.” Upload failures show in the sidebar.
  • Models. Pydantic models ChatTurn {role: "user" | "assistant", text} and UserQuery {question, filename, history=[]}.
  • Papers are identified by filename. It is the Qdrant payload filter key and the frontend's link between a selected paper and its chunks. PDFs themselves are never stored on the server, and the viewer uses a browser object URL.
  • Config constants in rag.py: HISTORY_EXCHANGES = 5, MAX_TOOL_ROUNDS = 1, MAX_CANDIDATE_CHUNKS = 500, TARGET_FRACTION = 0.33, model claude-sonnet-4-6.

How design choices get tested

Design choices are tested in a standalone offline harness, kept separate from the app's runtime code. It isn't in the app's GitHub repository, since it only runs locally to decide what to change in the app.

  • RAGAS

    Evaluates retrieval and generation quality. The plan is to use a Claude Sonnet judge.

  • LangSmith

    Tracks latency and API cost, including token counts, for each run.

  • Retrieval metrics

    Hit, recall, all-gold, precision, distinct documents and MRR, computed at several cutoffs by a script in the harness.

  • Cached generation

    Responses are cached on disk by a hash of the request, so reruns don't spend tokens twice.

The harness pipeline

Corpus and golden setConvert dataset rows into {id, question, answer, ground_truth_doc_ids} and a deduplicated corpus.
ChunkingFixed-size token windows with overlap: 256 tokens and 32 overlap, measured with the embedding model's tokenizer and mapped back to character offsets. Recursive and semantic chunkers were tested elsewhere.
EmbeddingBAAI/bge-small-en-v1.5 with normalized embeddings and the BGE query prefix, on GPU if available.
Vector storeA local Qdrant on port 6335, cosine distance, collection fixed256_bgesmall, with a payload index on doc_id.
RetrievalBatched top-50 queries, scored at several cutoffs.
GenerationClaude Haiku 4.5 at temperature 0 and 300 max tokens, with a strict “answer only from the context, otherwise say there isn't enough information” prompt and a context numbered [1] to [k]. Threaded across 4 workers.
Planned gridconfig with fixed seeds, then chunkers (fixed, recursive, semantic), then index and retrieve, then rerankers (none, cross-encoder, LLM), then generate with Haiku, then evaluate with RAGAS and a Sonnet judge, then cached results and a summary table.

Findings so far

Experiments

  • Chunking

    Three strategies were tested: fixed-size with a sliding window, recursive and semantic. Semantic chunking performed best, but only by a small margin.

  • Reranking in progress

    The reranker (“Rechunker”) shows notable gains, but it is slow to test. It adds an extra scoring pass, and the LLM variant adds extra model calls across the whole grid. This is the work taking up my time right now.

What's next

  1. Finish testing rerankers (none, cross-encoder and LLM) and decide whether the gains are worth the extra time and calls.
  2. Replace the 33% heuristic with relevance-based selection: a score threshold, reranking or an adaptive k.
  3. Move the app to the best chunker (semantic) and align its embedding model with the harness's.
  4. Read tables and figures. The PDF reader handles plain text only. The plan is to send table and figure images to the Claude API for a text description of each, then chunk and embed those descriptions with the prose so they can be retrieved like any other passage.
  5. Bring it back online once the design settles.

Longer term: more than one paper

The app handles one paper at a time. The planned extension is retrieval over clusters of papers, to understand how papers relate to each other as well as what each says alone.

  • Literature Review Assistant

    RAG over a small cluster of related papers for a systematic literature review. It would surface connections, contradictions and open questions, show reference chains as a graph with edge color and weight for relevance, and let a researcher add their in-progress work to the cluster to find gaps or strengthen a motivation section.

  • Topic-Scale Exploration

    The same idea across hundreds of papers on a broad topic, such as large language models. Subtopic clusters (attention mechanisms, tokenization, parsing algorithms) would emerge naturally and be shown with the same graph approach, to help narrow into a subtopic.

Running it locally

The hosted version is down, but the app runs locally.

# Backend (from Research_App_backend/)
pip install -r requirements.txt
# .env needs QDRANT_URL, QDRANT_API_KEY and ANTHROPIC_API_KEY
python main.py                  # http://127.0.0.1:8000

# Frontend (from Research_App_Frontend/)
npm install
# set VITE_API_URL=http://localhost:8000 in .env.local
npm run dev                     # http://localhost:5173

# Eval harness (from RAG Eval/transfer/)
# MultiHop_Setup.py -> index_baseline.py (needs local Qdrant on port 6335)
#   -> retrieve_eval.py -> generate.py

rag.py has a commented-out local Qdrant client (QdrantClient(host="localhost", port=6333)) as an alternative to Qdrant Cloud. It also calls create_payload_index on paper_chunks at import time, so that collection has to exist before the backend starts.
